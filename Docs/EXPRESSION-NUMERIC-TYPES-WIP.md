# Typed numeric expressions — partial implementation

Reference: Ikemen GO cb56d73badb322f3725257c2e8cfd157b2c3989d, compiler.go number/typedExp and bytecode.go mul/div/mod/add/sub. The compiler preserves integer versus decimal literals and converts to a controller parameter's requested type after evaluating the expression. Consequently a float parameter containing `1/4` receives zero, whereas `1.0/4` receives 0.25.

The actual WEB tokenizer now retains numeric literal type. Engine/expression-numeric-types.js evaluates closed numeric/variable expression subtrees using signed 32-bit integer arithmetic or float32 arithmetic. Supported typed subtrees include var/sysvar/fvar/sysfvar, unary plus/minus/not, addition/subtraction/multiplication/division/modulus, comparisons and logical and/or. Integer division truncates toward zero; integer arithmetic wraps; modulus converts both operands to integers; mixed numeric comparisons convert to float32. Unknown query/function subtrees remain on the previous evaluator rather than inventing their return type.

Tools/check-expression-numeric-types.mjs extracts the actual tokenizer/parser/evaluator from index.html. The before-change run failed on `1/4` (actual 0.25, native-expected zero); the focused after-change run passes. It also checks variable families, negative integer division, nested integer arithmetic, overflow, modulus conversion and float32 comparisons. The browser harness adds actual VelSet dispatch plus integer and decimal projectile-scale cases.

The broad regression exposed older fixtures that incorrectly expected decimal division from integer literals. The cornerpush fixture retains `1 / 4` and now expects native zero. Friction fixtures intended to exercise nonzero fractional friction now explicitly use `1.0 / 4`, retaining their expected 0.25. These are source-backed input/expectation corrections, not proof of complete expression compatibility.
